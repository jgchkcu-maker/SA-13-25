# Изменения расписания АК · СА-13-25

Python-проект для канала [«Расписание АК»](https://t.me/timetable_of_ak_sibsau).
Обычный подписчик читает канал через **Telethon от своего аккаунта**, а отдельный
Telegram-бот отправляет изменения **только для СА-13-25** в учебную группу.
Постоянно включённый компьютер или сервер не нужен: одна проверка запускается GitHub Actions.

**Проект нужно подключить к вашим ключам и аккаунту.** Без них реальную авторизацию,
распознавание фотографий и доставку в вашу группу проверить невозможно. Тесты проверяют
логику на искусственных данных и подставных API; это не проверка качества OCR на вашем расписании.

## Что уже реализовано

- Запуск каждые 20 минут: `7,27,47 * * * *` (UTC), плюс ручной запуск.
- Все новые посты после сохранённого указателя, с пагинацией без ограничения «последние 10».
- Все фото альбома в одном запросе распознавания; изображения, отправленные файлами, тоже скачиваются.
- Пауза 120 секунд для новых/отредактированных публикаций, чтобы альбом успел загрузиться.
- Повторная проверка **всех ранее отслеженных публикаций**, включая те, в которых группы сначала не было.
- Gemini `gemini-3.5-flash-lite`, структурированный JSON и дополнительная проверка строк в Python.
- Дата изменений, номер пары, предмет, преподаватель, кабинет; несколько дат в одном альбоме.
- Непонятные поля помечаются «не указан / неразборчиво». Неясная группа, дата или пара — строка пропускается.
- При отсутствии группы — тишина. Неразборчивые публикации повторно распознаются через 6 часов,
  максимум 3 попытки на версию; новая правка источника сбрасывает этот счётчик.
- Защита от повторных постов по нормализованному содержанию отдельных строк.
- При правке источника бот редактирует своё ранее отправленное сообщение.
- Если после правки данные исчезли/не читаются, прежнее сообщение помечается как неподтверждённое,
  без утверждения, что занятия отменены.
- Состояние в отдельной ветке `bot-state`, без зависимости от срока жизни Actions cache/artifacts.
- Ключи и сессия берутся только из окружения; в Actions — из GitHub Secrets.

Модель и поддержка изображений/JSON проверены по
[документации Google](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite).
Используется современный пакет `google-genai`, без устаревших параметров семплирования
[по инструкции миграции](https://ai.google.dev/gemini-api/docs/generate-content/whats-new-gemini-3.6).
Доступность модели для конкретного ключа и квоты проверяются уже реальным запуском.

## 1. Установка на Windows

Нужен Python **3.12 или 3.13**. В PowerShell в этой папке:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
Copy-Item .env.example .env
```

На Linux/macOS используйте `.venv/bin/python` и `.venv/bin/schedule-bot`.
`.env`, `*.secret` и `*.session*` исключены из Git. Не помещайте реальные значения в `.env.example`.

## 2. Создание бота и ключей

1. Создайте бота через [@BotFather](https://t.me/BotFather), получите токен.
2. Добавьте бота в учебную группу и разрешите ему отправлять сообщения.
   Права администратора и чтение переписки ему не требуются.
3. Получите `api_id` и `api_hash` на [my.telegram.org](https://my.telegram.org/apps).
   Это данные вашего приложения для **пользовательского** аккаунта, не токен бота.
4. Получите Gemini API key в [Google AI Studio](https://aistudio.google.com/api-keys).
5. Ваш пользовательский аккаунт должен иметь доступ к каналу-источнику.

Для справки: [сессии Telethon](https://docs.telethon.dev/en/stable/concepts/sessions.html),
[отправка и форматирование Telegram](https://core.telegram.org/bots/api#sendmessage).

## 3. Однократная авторизация Telethon

Заполните в локальном `.env` **только** `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`, затем:

```powershell
.\.venv\Scripts\schedule-bot.exe session
```

Введите телефон, код из Telegram и пароль двухэтапной защиты, если он включён.
Команда сохраняет `telegram-session.secret` и **не печатает сессию в консоль**.
Перенесите содержимое файла в Secret `TELEGRAM_SESSION` на GitHub; после переноса
удалите локальный файл, если он больше не нужен.

Сессия даёт доступ от имени аккаунта. Авторизуйтесь только на своём компьютере,
не присылайте файл/сессию в чат и не запускайте `session` в Actions.
При утечке завершите эту сессию в Telegram → Настройки → Устройства и создайте новую.

Чтобы узнать ID учебной группы, временно внесите сессию в локальный `.env` и выполните:

```powershell
.\.venv\Scripts\schedule-bot.exe dialogs
```

Найдите нужную группу в выводе и скопируйте её числовой ID целиком, обычно `-100...`.
Это список диалогов вашего аккаунта, выводите его только локально.
При переходе обычной группы в супергруппу Telegram меняет ID: настройте новый ID
и отдельную ветку состояния, чтобы старое состояние не смешалось с новым чатом.

## 4. Настройка GitHub

Файлы проекта уже находятся в этом репозитории. Он сейчас публичный, поэтому оставляйте
в нём только исходный код и инструкции. Ветка состояния зашифрована отдельным Secret
`STATE_ENCRYPTION_KEY`: без него расшифровать ID учебной группы, хеши строк и тексты сообщений нельзя.
Не загружайте `.venv`, `.env`, файлы сессии и папку `state`.

В **Settings → Secrets and variables → Actions → Secrets** создайте:

| Secret | Значение |
|---|---|
| `TELEGRAM_API_ID` | Ваш `api_id` |
| `TELEGRAM_API_HASH` | Ваш `api_hash` |
| `TELEGRAM_SESSION` | Содержимое `telegram-session.secret` одной строкой |
| `TELEGRAM_BOT_TOKEN` | Токен от BotFather |
| `TELEGRAM_CHAT_ID` | ID учебной группы целиком, вместе с минусом |
| `GEMINI_API_KEY` | Ключ Google AI Studio |
| `STATE_ENCRYPTION_KEY` | Сгенерированный вами уникальный ключ шифрования состояния |
| `TELEGRAM_THREAD_ID` | Необязательно: ID темы форума, куда отправлять сообщения |

Сгенерируйте `STATE_ENCRYPTION_KEY` локально одной командой и внесите результат сразу
в Secrets (значение не публикуйте и сохраните в менеджере паролей). Не теряйте и не меняйте
его: без ключа бот не сможет расшифровать сохранённое состояние и остановится.

```powershell
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

**Личный GitHub token создавать не нужно**: workflow использует автоматический `GITHUB_TOKEN`
с правом `contents: write`. Если организация запрещает это право или запрещает создание веток,
разрешите его для этого репозитория; ветка `bot-state` должна допускать запись workflow.

В **Variables** можно дополнительно задать:

| Variable | По умолчанию |
|---|---|
| `TELEGRAM_SOURCE` | `@timetable_of_ak_sibsau` |
| `GEMINI_MODEL` | `gemini-3.5-flash-lite` |
| `INITIAL_LOOKBACK_DAYS` | `3` — сколько дней истории обработать при первом запуске |

Для приватного источника используйте числовой ID из `dialogs`, а не invite-ссылку.
Изменения постов **до начального окна**, которые бот никогда не видел, не отслеживаются.
Все публикации, попавшие в начальное окно или появившиеся после него, остаются отслеживаемыми.

## 5. Первый запуск

1. Откройте **Actions → Schedule watcher → Run workflow** в основной ветке репозитория.
2. Выберите `operation: initialize`. Это создаст ветку `bot-state` и пустое состояние;
   в Telegram ничего не отправляется. Инициализация не перезаписывает существующее состояние.
3. Запустите тот же workflow с `operation: run`.
4. Дождитесь зелёного статуса. Если среди фотографий за последние 3 дня есть уверенно
   распознанные строки для СА-13-25, бот отправит их в группу.
5. После этого проверки выполняются по расписанию автоматически.

Расписание работает из основной ветки. GitHub может задерживать или пропускать запуски при
нагрузке; это **интервал планировщика, а не гарантия точной доставки каждые 20 минут**.
Следующий успешный запуск дочитает пропущенные новые посты по сохранённому ID.
См. [ограничения schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
Для публичных неактивных репозиториев GitHub также может отключать расписание.
В приватном репозитории учитывайте лимит минут Actions и квоты/оплату Gemini своего аккаунта.

## Локальная проверка

После заполнения всех полей `.env`:

```powershell
.\.venv\Scripts\schedule-bot.exe init-state
.\.venv\Scripts\schedule-bot.exe run
```

**Команда `run` действительно отправляет сообщения.** Для локальной проверки укажите отдельный
тестовый чат. Не запускайте локальный и GitHub экземпляры с разными состояниями в одну группу:
они не знают об отправках друг друга.

## Состояние и защита от дублей

После расшифровки `bot-state:state.json` содержит указатель истории, ID публикаций и их версии,
хеши уже отправленных строк, ID/тексты сообщений бота и единственную незавершённую операцию
`pending`. В публичной ветке виден только шифротекст. Ключей API, сессии, телефона и фотографий
в состоянии нет. Фото скачиваются во временную папку и удаляются по завершении;
большие альбомы временно загружаются через Gemini Files API и удаляются после распознавания.

Перед каждой отправкой сохраняется намерение, после ответа Telegram — ID сообщения.
Редактирование с известным ID можно безопасно повторить. У Bot API `sendMessage` нет ключа
идемпотентности: если соединение оборвалось после принятия сообщения Telegram, нельзя достоверно
узнать результат по одному ответу HTTP. В этом случае **бот останавливается, не отправляя дубль**.

Для восстановления:

1. Проверьте последние сообщения бота в учебной группе и сравните их с изменением источника.
2. **Actions → Schedule watcher → Run workflow → operation: resolve**.
3. Если сообщение доставлено, укажите его ID в `delivered_message_id` (последнее число ссылки
   на сообщение в супергруппе). Поле `confirm_not_delivered` оставьте выключенным.
4. Только если вы проверили, что сообщения в группе **нет**, включите `confirm_not_delivered`,
   оставив ID пустым. Тогда следующий запуск повторит отправку.
5. Запустите `operation: run`. Не удаляйте состояние ради восстановления.

Потеря/повреждение состояния останавливает бот, а не запускает рассылку истории заново.
Не отменяйте workflow во время отправки; параллельные запуски сериализованы `concurrency`.
Не удаляйте сообщения бота вручную: их ID нужны для последующих исправлений.
Имена групп `СА 13 25`, `СА1325`, `СА-13/25`, латинские `CA` и разные тире нормализуются.
Сокращение `СА-13` без года сознательно не принимается: по нему нельзя надёжно отличить поток.

## Разработка и проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\ruff.exe check .
```

`requirements.lock` фиксирует весь проверенный набор зависимостей, включая инструменты тестов.
CI проверяет Python 3.12 и 3.13. Тесты не требуют ключей и не отправляют сообщения.
Проверяются альбомы, начальное окно, отложенная публикация, старые правки, отсутствие группы,
неразборчивые поля, HTML, лимит сообщения, дубли, сбой OCR, потеря ответа отправки,
восстановление правок, локальное/удалённое состояние и отсутствие секретов в HTTP-ошибках.

Код разбит на `telegram.py` (чтение и доставка), `recognition.py` (Gemini),
`models.py` (строгая фильтрация), `formatting.py` (оформление), `engine.py` (обработка)
и `state.py` (постоянное хранение).

OCR остаётся вероятностным: инструкция модели и проверки снижают риск ошибок, но не дают
математической гарантии правильного чтения фотографии. У каждого уведомления есть ссылка
на оригинал. Для проверки качества на реальных таблицах нужен пробный запуск с вашими ключами.
